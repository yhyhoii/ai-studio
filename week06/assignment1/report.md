# 프롬프트 3기법 비교 리포트

## 1. 과업 정의
- 선택: (나) 리뷰 분류
- 분류 항목: 배송 / 품질 / 가격 / 서비스 / 기타
  - 배송: 배송 속도·지연, 포장·운송 중 파손
  - 품질: 고장, 마감, 재질, 내구성 등 제품 자체
  - 가격: 비싸다·저렴하다·가성비
  - 서비스: 고객센터·상담 응대, 환불·교환 처리
  - 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우
- 긴급도 기준 (얼마나 빨리 대응해야 하는 리뷰인가)
  - 3 (즉시 대응): 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
  - 2 (빠른 확인): 불만은 있지만 구체적인 요구가 없음
  - 1 (참고): 칭찬, 단순 의견, 취향 표현
- 출력 형식: `{"type": "...", "urgency": 1~3}`

## 3. 프롬프트 전문
세 프롬프트 모두 같은 분류 기준·긴급도 기준·출력 형식을 사용한다. `{리뷰}` 자리에 테스트 문장을 넣어 실행한다.

### Zero-shot
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

출력은 아래 JSON 한 줄만 쓴다. 설명, 코드블록(```)은 쓰지 않는다.
{"type": "유형", "urgency": 숫자}

리뷰: "{리뷰}"
```

### Few-shot
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

출력은 아래 JSON 한 줄만 쓴다. 설명, 코드블록(```)은 쓰지 않는다.
{"type": "유형", "urgency": 숫자}

[예시]
리뷰: "주문 다음 날 아침에 바로 받았어요."
{"type": "배송", "urgency": 1}

리뷰: "세탁 한 번 했더니 실밥이 다 풀렸어요. 반품할게요."
{"type": "품질", "urgency": 3}

리뷰: "다른 사이트보다 만 원이나 비싸게 샀네요."
{"type": "가격", "urgency": 2}

리뷰: "선물용으로 하나 더 주문했습니다."
{"type": "기타", "urgency": 1}

리뷰: "택배가 늦어서 문의했더니 상담원분이 바로 해결해 주셨어요."
{"type": "서비스", "urgency": 1}

리뷰: "{리뷰}"
```

### CoT
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

아래 단계에 따라 추론을 먼저 쓴다.
1단계: 리뷰에 등장하는 화제를 모두 찾는다.
2단계: 반어법·과장이 있는지 보고, 고객의 실제 감정(긍정/부정)을 판단한다.
3단계: 유형 기준에 따라 주된 유형을 하나 고른다.
4단계: 긴급도 기준에 따라 긴급도를 정한다.

마지막 줄에는 JSON 한 줄만 쓴다. 마지막 줄에는 다른 글자나 코드블록(```)을 붙이지 않는다.
{"type": "유형", "urgency": 숫자}

리뷰: "{리뷰}"
```

## 6. 분석

### 요약
| 기법 | 형식 준수 | 유형 정확 | 긴급도 정확 | 반복 일관성 (#4) | 출력 길이 |
|---|---|---|---|---|---|
| Zero-shot | 5/5 | 3/5 | 4/5 | 3/3 동일 | JSON 한 줄 (약 30자) |
| Few-shot | 5/5 | 3/5 | 4/5 | 3/3 동일 | JSON 한 줄 (약 30자) |
| CoT | 5/5 | 3/5 | 4/5 | 2/3 (유형 흔들림) | 추론 4단계 + JSON (약 400~600자) |

### 형식 준수
- 세 기법 모두 21회 전부 `json.loads()`로 읽을 수 있는 출력을 냈다. Zero-shot과 Few-shot은 JSON 한 줄만, CoT는 추론 뒤 마지막 줄에 JSON만 썼다.
- 코드펜스(```)나 "물론입니다!" 같은 사족은 한 번도 나오지 않았다. 세 프롬프트 모두 "설명·코드블록을 쓰지 않는다", CoT는 "마지막 줄에는 다른 글자를 붙이지 않는다"를 명시한 효과로 본다.
- 다만 CoT는 응답 전체를 바로 `json.loads()`에 넣으면 실패하고, **마지막 줄만 잘라내는 후처리가 반드시 필요**하다. 프로그램 연동 측면에서는 Zero-shot·Few-shot이 더 단순하다.

### 분류 정확성
- 명확한 사례(#1~#3)는 세 기법 모두 유형·긴급도를 정확히 맞혔다. 차이는 애매 사례에서만 나타났다.
- **#4 (질문형 불량 의심)**: 나는 "이렇게 작동하나요"를 불량 의심으로 보고 품질로 판단했지만, 세 기법 모두 대부분 **기타**로 분류했다. CoT 추론을 보면 "작동과 관련된 내용이라 품질로 볼 여지도 있지만, 리뷰 전체가 질문이고 기준에서 '질문'은 기타"라고 두 해석을 모두 검토한 뒤 기준 문구를 따랐다. 긴급도는 "불만은 있지만 구체적인 요구가 없음"을 근거로 세 기법 모두 내 정답과 같은 2를 냈다.
- **#5 (배송 긍정 + 사용 후 애매함)**: 나는 뚜렷한 불만이 없는 단순 의견으로 보고 기타 / 1로 판단했지만, 세 기법 모두 **품질 / 2**로 분류했다. CoT는 "'~는데'로 이어지는 문장이라 무게가 뒤쪽에 실려 있고, 모든 요소가 긍정인 경우가 아니므로 기타에 해당하지 않는다"고 판단했다.
- 두 사례 모두 **모델은 내가 쓴 기준 문구를 글자 그대로 적용했고, 나는 기준에 적지 않은 직관으로 정답을 정했다.** 기준에는 "질문 형태로 불량을 의심하는 경우"나 "긍정과 부정이 섞였을 때 주된 화제를 고르는 법"이 없었다. 애매 사례의 오답은 기법의 차이보다 **분류 기준의 빈틈**에서 나왔다.
- Few-shot은 Zero-shot과 결과가 완전히 같았다. 예시 5개에 질문형이나 긍정·부정 혼합 사례가 없어서, 이번 애매 사례의 판단에 참고할 패턴을 주지 못했다. Few-shot의 효과는 **예시가 실제로 헷갈리는 경계 사례를 담고 있을 때** 나타난다는 점을 확인했다.

### 일관성
- #4 반복 실행에서 Zero-shot과 Few-shot은 3회 모두 같은 답(기타 / 2)이었다.
- **CoT만 3회차에서 유형이 품질로 바뀌었다.** 1·2회차 추론은 "질문이므로 기타", 3회차는 "질문의 핵심은 제품 이상 작동이므로 품질"로 결론이 갈렸다. CoT는 매번 두 해석을 새로 따져 보기 때문에, 기준이 정하지 않은 경계 사례에서는 추론 경로에 따라 결론이 흔들렸다.
- 반대로 보면, CoT의 흔들림은 **이 입력이 기준상 애매하다는 신호**로 쓸 수 있다. Zero-shot·Few-shot은 일관되게 답했지만, 일관되게 내 정답과 달랐다. 일관성이 높다고 해서 정확하다는 뜻은 아니다.

### 비용
- Zero-shot과 Few-shot은 JSON 한 줄(약 30자)만 출력했지만, CoT는 4단계 추론까지 약 400~600자를 출력했다. 출력 토큰은 입력보다 단가가 비싸므로, 리뷰 1,000건을 처리하면 CoT의 비용이 가장 크다.
- Few-shot은 예시 5개만큼 입력 토큰이 늘지만 출력은 Zero-shot과 같다.
- 이번 실험에서 CoT의 추가 비용은 정확도 향상으로 이어지지 않았다. 대신 **판단 근거를 보여 주는 가치**가 있었다. #4·#5에서 모델이 왜 내 정답과 다르게 판단했는지는 CoT 추론을 통해서만 알 수 있었다.

### 한계
- 테스트 입력이 5건이고 한 챗봇(Claude.ai)에서만 실행했다. 다른 모델에서는 결과가 다를 수 있다.
- 무료 챗봇 UI라서 temperature와 실제 토큰 수를 확인할 수 없어, 비용은 출력 길이로 추정했다.

## 7. 결론 — 우리 팀이 쓸 기본 전략
**기본은 "경계 사례 규칙을 보강한 기준 + 경계 사례를 담은 Few-shot"으로 하고, CoT는 애매 건 검수용으로만 쓴다.**

1. **분류 기준에 경계 사례 규칙을 명시한다.** 이번 오답은 모두 기준이 정하지 않은 경계(질문형 불량 의심, 긍정·부정 혼합)에서 나왔다. 예: "질문 형태라도 제품 이상을 의심하면 품질", "긍정과 부정이 섞이면 부정 쪽 화제를 주된 유형으로" 같은 규칙을 기준에 추가한다. 팀 캡스톤에서도 카테고리 정의와 경계 처리 규칙을 문서로 먼저 합의한다.
2. **기본 기법은 Few-shot, 단 예시에 경계 사례를 넣는다.** 이번 Few-shot은 명확한 예시만 있어 Zero-shot과 차이가 없었다. 예시 중 1~2개를 실제로 헷갈리는 경계 사례로 채워야 예시가 판단 기준 역할을 한다. 출력이 JSON 한 줄이라 비용이 낮고 파싱도 단순하다.
3. **CoT는 애매 건 검수와 디버깅에만 쓴다.** 출력이 10배 이상 길고 경계 사례에서 결론이 흔들렸다. 대량 분류에는 쓰지 않고, 모델과 사람의 판단이 갈리는 건을 다시 보거나 기준의 빈틈을 찾을 때 사용한다. 근거가 필요하면 JSON 안에 짧은 `"reason"` 칸을 두는 방식도 검토한다.
4. **형식이 지켜져도 코드에서 방어한다.** 이번 21회는 형식이 모두 지켜졌지만, LLM 출력은 확률적이므로 파싱 예외 처리와 값 검증(과제 2의 3중 방어)을 항상 둔다.
