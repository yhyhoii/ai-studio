# 프롬프트 3기법 비교 리포트

## 1. 과업 정의
- 선택: (나) 리뷰 분류
- 분류 항목: 배송 / 품질 / 가격 / 서비스 / 기타
  - 배송: 배송 속도·지연, 포장·운송 중 파손
  - 품질: 고장, 마감, 재질, 내구성 등 제품 자체
  - 가격: 비싸다·저렴하다·가성비
  - 서비스: 고객센터·상담 응대, 환불·교환 처리
  - 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우
- 긴급도 기준 (얼마나 빨리 대응해야 하는 리뷰인가)
  - 3 (즉시 대응): 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
  - 2 (빠른 확인): 불만은 있지만 구체적인 요구가 없음
  - 1 (참고): 칭찬, 단순 의견, 취향 표현
- 출력 형식: `{"type": "...", "urgency": 1~3}`

## 3. 프롬프트 전문
세 프롬프트 모두 같은 분류 기준·긴급도 기준·출력 형식을 사용한다. `{리뷰}` 자리에 테스트 문장을 넣어 실행한다.

### Zero-shot
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

출력은 아래 JSON 한 줄만 쓴다. 설명, 코드블록(```)은 쓰지 않는다.
{"type": "유형", "urgency": 숫자}

리뷰: "{리뷰}"
```

### Few-shot
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

출력은 아래 JSON 한 줄만 쓴다. 설명, 코드블록(```)은 쓰지 않는다.
{"type": "유형", "urgency": 숫자}

[예시]
리뷰: "주문 다음 날 아침에 바로 받았어요."
{"type": "배송", "urgency": 1}

리뷰: "세탁 한 번 했더니 실밥이 다 풀렸어요. 반품할게요."
{"type": "품질", "urgency": 3}

리뷰: "다른 사이트보다 만 원이나 비싸게 샀네요."
{"type": "가격", "urgency": 2}

리뷰: "선물용으로 하나 더 주문했습니다."
{"type": "기타", "urgency": 1}

리뷰: "택배가 늦어서 문의했더니 상담원분이 바로 해결해 주셨어요."
{"type": "서비스", "urgency": 1}

리뷰: "{리뷰}"
```

### CoT
```
다음 고객 리뷰를 분류하라.

[유형] 배송 / 품질 / 가격 / 서비스 / 기타 중 하나
- 배송: 배송 속도·지연, 포장·운송 중 파손
- 품질: 고장, 마감, 재질, 내구성 등 제품 자체
- 가격: 비싸다·저렴하다·가성비
- 서비스: 고객센터·상담 응대, 환불·교환 처리
- 기타: 사실 진술, 질문, 단순 의견, 여러 요소가 모두 긍정인 경우

[긴급도] 1~3
- 3: 고장, 파손, 오배송, 심한 지연, 환불·교환 요구, 강한 불만
- 2: 불만은 있지만 구체적인 요구가 없음
- 1: 칭찬, 단순 의견, 취향 표현

아래 단계에 따라 추론을 먼저 쓴다.
1단계: 리뷰에 등장하는 화제를 모두 찾는다.
2단계: 반어법·과장이 있는지 보고, 고객의 실제 감정(긍정/부정)을 판단한다.
3단계: 유형 기준에 따라 주된 유형을 하나 고른다.
4단계: 긴급도 기준에 따라 긴급도를 정한다.

마지막 줄에는 JSON 한 줄만 쓴다. 마지막 줄에는 다른 글자나 코드블록(```)을 붙이지 않는다.
{"type": "유형", "urgency": 숫자}

리뷰: "{리뷰}"
```

## 6. 분석

### 요약
| 기법 | 형식 준수 | 유형 정확 | 긴급도 정확 | 반복 일관성 (#4) | 출력 길이 |
|---|---|---|---|---|---|
| Zero-shot | 5/5 | 5/5 | 4/5 | 3/3 동일 | JSON 한 줄 (약 30자) |
| Few-shot | 5/5 | 5/5 | 4/5 | 3/3 동일 | JSON 한 줄 (약 30자) |
| CoT | 5/5 | 5/5 | 4/5 | 3/3 동일 | 추론 4단계 + JSON (약 400~600자) |

### 형식 준수
- 세 기법 모두 21회 전부 `json.loads()`로 읽을 수 있는 출력을 냈다. Zero-shot과 Few-shot은 JSON 한 줄만, CoT는 추론 뒤 마지막 줄에 JSON만 썼다.
- 코드펜스(```)나 "물론입니다!" 같은 사족은 한 번도 나오지 않았다. 세 프롬프트 모두 "설명·코드블록을 쓰지 않는다", CoT는 "마지막 줄에는 다른 글자를 붙이지 않는다"를 명시한 효과로 본다.
- 다만 CoT는 응답 전체를 바로 `json.loads()`에 넣으면 실패하고, **마지막 줄만 잘라내는 후처리가 반드시 필요**하다. 프로그램 연동 측면에서는 Zero-shot·Few-shot이 더 단순하다.

### 분류 정확성
- 명확한 사례(#1~#3)는 세 기법 모두 유형·긴급도를 정확히 맞혔다.
- 애매 사례 #4(반어법)는 세 기법 모두 "돈 굳었네요 야호"를 칭찬이나 가격 평가로 오해하지 않고 **배송 / 3**으로 정확히 판단했다. CoT 추론을 보면 "'돈 굳었네요'는 가격 평가가 아니라 지연을 비꼬는 표현"이라고 가격 오분류 가능성을 직접 검토한 뒤 배제했다. 애매함이 실제로 존재했고, 모델이 그것을 인식하고 해결했다는 근거다.
- 애매 사례 #5는 세 기법 모두 유형은 **품질**로 맞혔지만 긴급도는 내 정답(1)과 달리 **2**로 판단했다. CoT 4단계는 "불만은 분명하지만 고장·환불 요구 같은 구체적 사안이나 요구가 없다"는 근거를 들었다. 이는 내가 정한 기준 "2: 불만은 있지만 구체적인 요구가 없음"에 정확히 들어맞는다. 즉 틀린 쪽은 모델이 아니라 **내 정답 라벨**이었다. 실행 전에는 '체념'을 '단순 의견(1)'으로 봤지만, 기준을 글자 그대로 적용하면 2가 맞다.
- 이 결과는 LLM 분류의 품질이 프롬프트 기법보다 **분류 기준(라벨 정의)의 명확성**에 더 크게 좌우된다는 점을 보여 준다. 기준이 모호하면 사람이 붙인 정답부터 흔들린다.

### 일관성
- 반복 실행한 #4는 세 기법 모두 3회 내내 같은 답(배송 / 3)이었다. CoT는 추론 문장의 표현이 매번 달랐지만 결론은 같았다.
- 세 프롬프트 모두 분류 기준·긴급도 기준을 상세히 정의해 두었기 때문에, 모델이 매번 같은 규칙을 적용할 수 있었던 것으로 본다. 기준을 구체적으로 적는 것만으로도 무료 챗봇(temperature 조절 불가) 환경에서 높은 일관성을 얻을 수 있었다.

### 비용
- 같은 정답을 내는 데 Zero-shot과 Few-shot은 JSON 한 줄(약 30자)만 출력했지만, CoT는 4단계 추론까지 약 400~600자를 출력했다. 출력 토큰은 입력보다 단가가 비싸므로, 리뷰 1,000건을 처리하면 CoT의 비용이 가장 크다.
- Few-shot은 예시 5개만큼 입력 토큰이 늘지만 출력은 Zero-shot과 같다.
- 이번 실험에서는 Few-shot의 예시와 CoT의 추론이 **정확도를 더 높이지 못했다**. Zero-shot만으로 이미 같은 결과가 나왔기 때문이다.

### 한계
- 테스트 입력이 5건이고 한 챗봇(Claude.ai)에서만 실행했다. 더 약한 모델이나 기준이 짧은 프롬프트에서는 기법 간 차이가 더 크게 나타날 수 있다.
- 무료 챗봇 UI라서 temperature와 실제 토큰 수를 확인할 수 없어, 비용은 출력 길이로 추정했다.

## 7. 결론 — 우리 팀이 쓸 기본 전략
**기본은 "상세한 분류 기준 + Few-shot"으로 하고, CoT는 필요할 때만 쓴다.**

1. **분류 기준을 먼저 명확히 정의한다.** 이번 실험에서 정확도를 좌우한 것은 기법이 아니라 기준의 명확성이었다(#5 긴급도). 팀 캡스톤에서도 카테고리·등급의 정의와 경계 사례 처리 규칙을 문서로 먼저 합의한다.
2. **기본 기법은 Few-shot.** 이번에는 Zero-shot과 결과가 같았지만, 비용 증가는 입력 쪽 예시 몇 개뿐이다. 예시는 출력 형식과 경계 사례 판단을 고정하는 안전장치이므로, 모델이 바뀌거나 입력이 다양해지는 실제 서비스에서 형식 이탈을 줄이는 데 유리하다.
3. **CoT는 판단 근거가 필요할 때만 쓴다.** 정확도는 같았지만 출력이 10배 이상 길고 마지막 줄 파싱이 따로 필요하다. 대량 분류에는 쓰지 않고, 애매 건 검수나 프롬프트 디버깅처럼 "왜 그렇게 판단했는지"를 봐야 할 때만 사용한다. 근거가 필요하면 JSON 안에 짧은 `"reason"` 칸을 두는 방식도 검토한다.
4. **형식이 지켜져도 코드에서 방어한다.** 이번 21회는 형식이 모두 지켜졌지만, LLM 출력은 확률적이므로 파싱 예외 처리와 값 검증(과제 2의 3중 방어)을 항상 둔다.
